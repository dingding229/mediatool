# 备份、演练、恢复与回滚

[文档目录](../INDEX.md) · [运维页面](../guide/ops.md)

## 备份包含什么

“运维 → 备份与告警 → 备份管理”可创建系统备份、查看结果、下载、固定和按条件删除。

备份包含同一只读数据库快照、清单及已登记的受管 STRM/NFO/字幕。输出缺失、摘要不符、越界或被手工修改时会明确失败。**不包含应用主密钥、115 原媒体、下载器做种源，以及 Emby、CloudDrive2、下载器的外部配置和卷。** 这些内容必须独立保管。

数据库备份可能包含敏感内容，私有保存，不提交版本库或公开共享。主密钥与备份分开保管，恢复时必须匹配。固定备份及正在演练或维护单引用的备份不能自动删除；保留策略至少保留最近两份成功备份。

## 创建与下载

1. 点击“创建系统备份”，确认范围。
2. 等待排队和执行；查看“备份详情”，不能把已排队当作备份成功。
3. 备份就绪后可“下载备份”并保存在自己的私有存储。
4. 需要自动执行时，在“维护策略”配置备份计划和保留范围。

## 恢复演练

点击“恢复演练”，程序在专属临时数据库恢复并核对数据，不覆盖业务库，任务进程也不连接该临时库。演练要求数据库角色有创建数据库权限。

正常结束只清理自己创建的临时库；中断后由维护界面核对创建记录，符合条件才可“清理临时库”。不能对未知数据库做自动删除。

宿主命令也可核对备份：

```sh
./media-toolctl --root "$PWD" backup-verify
./media-toolctl --root "$PWD" --archive /私有备份目录/backup.dump backup-verify
```

这只验证备份内容和恢复可读性，不代表全部外部服务和真实媒体已经恢复。

## 正式恢复或回滚

1. 在“恢复与回滚”选择成功备份或已登记版本，点击“预览恢复 / 预览回滚”。
2. 核对范围与保护条件，输入提示的精确确认短语，点击“审批维护单（不立即执行）”。
3. 部署所有者在实际部署根目录运行页面给出的命令：

```sh
./media-toolctl --root "$PWD" execute <维护单编号>
```

4. 执行器重新检查批准、时限、镜像与数据保护条件，先备份，再暂停业务并等待在执行任务结束。
5. 执行后在页面核验结果，重新登录并检查业务；只有核对完成后才解除维护。批准和执行完成都不自动解除维护。

恢复只补回可核对的缺失输出，不覆盖不同内容的现存文件；保留原数据库和切换前资料。账号会话会撤销，旧任务暂停，通知不会因恢复自动重发。

受控恢复要求备份满足近期演练、数据结构及受保护数据一致等条件；凭据、授权或媒体归属变化会阻止恢复。数据库不可读或条件不满足时，由所有者离线人工处理，不能绕过保护强行覆盖。

## 网页直接恢复（schema 75起，与上述命令行方式并列）

在“运维 → 备份与告警 → 恢复与回滚 → 网页备份恢复”选择就绪备份。页面显示来源、时间、schema、
大小、SHA256与校验状态。先预览：校验包完整性、主密钥匹配、全部密文、恢复后的向上迁移；
备份高于当前schema拒绝。低schema只在独立候选库迁移，成功后才导入业务库。

重新登录（10分钟内）后，预览中点击确认并输入 `恢复 <完整备份编号>`，排队执行。
202不是成功，请查看执行记录。无需docker.sock或宿主命令：app内使用已有PG客户端，
跨实例锁暂停调度、插件进程和业务写入，等待运行任务结束（最多120秒）。
先创建并自动保护“恢复前快照”，失败中止。候选库核对完成后，以单个PG事务导入，不切换DSN、不DROP DATABASE。
导入/核验失败自动恢复该快照；失败回滚仍失败则保持维护unknown，不硬推、不自动重放。
成功/已核对的失败恢复业务调度，恢复前快照保留，最近一份不可取消固定或删除。
在执行记录点击“预览回滚到恢复前”，仍走完整预览、确认、快照、异步执行流程。

### 精确包含/排除范围

- **包含**：`database.dump`中通过保护核验的业务历史；`outputs.tar`中已登记且摘要正确、当前缺失的受管STRM/NFO/字幕；`manifest.json`。
- **保留当前、不回退**：运维记录/策略、插件实例/权限/配置/加密KV及工作流记录。
- **拒绝差异**：管理员/媒体账号、115授权、连接凭据、应用设置、播放器策略/稳定访问凭据、媒体归属与受管输出登记等保护表；不因恢复回退授权或凭据。
- **绝不覆盖**：现存STRM正文和其他现存输出（不同摘要拒绝，已相同则不写）；主密钥、Compose、环境变量、其他 `/data`配置。
- **不包含也不处理**：115原媒体、`downloads/`、`qbittorrent-downloads/`、`logs/`、Emby/CloudDrive2/下载器配置与外部卷。
- 缺失输出仅补回，不下载云端媒体或字幕正文；失败后已补回的、核验过的缺失输出保留，不删除媒体文件。

主密钥独立保管。包中key fingerprint必须匹配当前主密钥，且候选库全部密文必须可解密，否则拒绝。
恢复成功撤销管理端/媒体端旧会话，旧pending/running任务暂停、通知与插件未决执行标unknown，必须逐项核对，不能自动重放。
进程中断后执行记录变unknown，维护保持；“核对中断结果”检查PG维护客户端已退出及与业务导入同事务的提交标记，
不再执行恢复。无法证明时保留维护及快照，使用命令行核对私有备份。应用需有现有演练要求的CREATE DATABASE权限与空间，
候选库名称限定为本次随机ID，正常及失败路径只清理本次候选；进程硬中断的孤儿候选库由所有者离线核对后清理，不自动删除未知库。

B4 导出/导入只处理 PostgreSQL `public` 业务 schema，不删除或恢复其他 schema。
管理端认证表和运维进度/策略表在导入期间保留在线；事务提交标记随业务数据一同提交，
因此可持续查询状态，完成后才撤销旧管理会话。自动保护最近一份就绪恢复前快照；
旧快照按保留策略处理，手动固定仍保留，不把所有历史快照永久固定。

在线保留表：全部 `ops_*` 运维表（只有 `ops_restore_commit` 是随业务导入的原子提交标记）、
全部 `administrator_*` 认证/恢复标记表，以及 `open115_authorizations`、`integrations`。
后两者原本就要求保护摘要一致；保留其原表还避免外键DDL锁阻塞管理会话读取。
其他schema完全不参与导入，既有输出只补缺失、不回滚文件正文。
