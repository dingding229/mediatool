# 跨版本未完成输出：核对、明确迁移与入库恢复

日期：2026-10-11。源码不新增数据库迁移，保持迁移20。是否已发布以output-recovery-*报告为准。

## 要解决的问题

非连续合集从旧E01E03链改为两个独立索引后，旧任务若重跑，不能把旧输出留在原地、同时追加新别名，再将不完整/错误布局算作入库成功。同样，恢复过程不能因重新查询元数据而覆盖用户已经明确修正的资产身份。

本模块在事务内核对整个既有STRM集合，非空集合必须与初始入库拟生成集合完全一致；新旧布局不同或缺失某个别名都停止，不部分追加。旧布局检测先于TMDB网络调用，另在资产锁内stage前再次核对，避免只靠一次不锁定预检查。

## 状态与用户操作

1. 上传仍按原RPC控制/哈希校验执行。布局发生冲突时，已校验传输转为`needs_output_reconciliation`，下载文件也记录这一状态。
2. 此类错误带明确operator-required标记，原Job变成paused，不按指数退避反复尝试。普通重试、恢复上传、绑定或重新创建会话不能绕过。
3. 下载与传输页面显示“核对入库恢复”。只读预览展示资产ID、原输出、应有布局和阻断原因，不写文件、不创建上传、不返回STRM正文或Key。
4. 旧输出仍有pending/conflict日志时，先在云盘索引恢复原意图/核对手工内容。原文件丢失但日志已applied且加密正文已清除时，不猜测重新生成，需人工处理或既有明确Key轮换/重建流程；不能把“applied标签”当作文件存在。
5. 旧命名与实际覆盖不一致时，链接会按assetId聚焦云盘索引。使用已有身份修正/输出迁移预览，查看新索引与旧归档后明确确认；共享NFO、网盘媒体、做种源文件及文件Key仍按原迁移边界保护。
6. 返回下载页面重新核对，只有完整、已确认且真实文件/授权相符的布局才能点击“明确恢复入库（不重新上传）”。接口需要当前controlRevision与planDigest。
7. 批准持久化为`output_resume_approved`与专用`transfer.import.resume`队列Job。同一批准回放只查询相同阶段，不再新增工作；修复之后重新批准使用新的控制修订号作为幂等键，不复用已耗尽/暂停的旧Job。
8. 专用Worker执行前重新核对证明；旧批准、文件/授权/绑定/源目录/源字幕变化会暂停等待核对。它不取新影视身份、不重写STRM/NFO、不上传媒体，只以现有路径补齐受控字幕、完成本地文件入库阶段，再走原Emby刷新/逐路径可见性确认。传输imported并不等于整个下载任务在Emby可见或播放器解码通过。

## 证明和范围

预览/Worker核对：真实下载文件绑定、云端present状态/校验大小/连接/目标路径、已确认资产身份与revision、完整集号集合、实际STRM正文摘要及有效文件级授权、所有资产所有的NFO/字幕摘要、pending日志、当前输出根目录、共享做种目录映射，以及整组源字幕内容摘要。证明只返回SHA256，不返回原始URL/Token、Provider消息、绝对下载路径或文件正文。

已确认目录/版次名称可以保留，恢复按真实覆盖核对现有路径，而不是强行再命名一次；每个声明集号必须精确覆盖且不能重复/遗漏。源字幕读为有限普通文件（idx/sub配对、500文件/64MiB总复制），写入前用同一缓冲的摘要与批准内容核对。原视频只检查目录内普通文件和已记录大小，不声称再次完整计算视频hash或验证播放器解码。程序不会移动/删除做种源文件。

固定STRM与NFO摘要核对拒绝最终符号链接、非普通文件、手工改动或未知所有权；控制修订/资产锁阻止本程序的并发身份变更。仍不声称能抵御拥有输出目录写权限的恶意进程持续替换文件，或外部管理员直接篡改数据库。源文件/源字幕在检查后被外部进程修改可能导致暂停，不代表批准可无限重放。

## 后台候选恢复

云盘候选的原加密意图仍按既有规则恢复，但FinalizeRecovered必须再次核对完整消费覆盖和实际托管STRM内容。旧稀疏链转为needs_output_reconciliation，显示在“待确认/需明确迁移”列表并带已有assetId，不再作为新候选重确认，也不因NFO意图已applied就提前confirmed。完成明确迁移后才能最终确认/刷新。

上传验证围栏只保护RPC及其验证记录；进入入库前释放上传围栏，再按传输/资产顺序取得入库锁，避免同一任务跨PG连接自锁。该行为经原完整隔离下载→上传→入库fixture复核，未通过放宽租约或取消暂停来绕过。

## API

- GET `/api/v1/transfers/{id}/output-preview`：管理员只读预览。
- POST `/api/v1/transfers/{id}/resume-import`：Body `{controlRevision,planDigest}`，同源/CSRF保护，明确批准专用入库恢复。
- GET `/api/v1/media/assets?assetId=<UUID>&page=1&pageSize=50`：聚焦已确认资产，参数空/重复/错误UUID均拒绝，仍不返回文件Key。

批准响应成功表示已持久化/排队，不是媒体播放成功。网络结果不确定时用“重新核对”读回当前状态，不自动换证明重复创建请求；目前没有新增后台清理或自动输出迁移任务。

## 验证与待完成

真实部署不创建旧任务示例、不代迁移/恢复现有媒体。实际自有PT资源、qBittorrent/订阅/外部通知、完整设备/普通用户权限、长期稳定性和容量仍是全项目门槛，不能以此恢复模块实现替代。


## 已提交原清单的正常重试

存在strm_entries的verified/artifacts_pending任务不会再次向TMDB取新模板或用旧任务名称重写资产。它只重放原加密pending意图、核对已确认布局/当前文件/有效授权/源字幕，继承原路径、身份和STRM正文。旧布局仍转人工门槛，手工修改/缺失/root映射改变仍阻断；没有将新的提供方简介覆盖已经确认的NFO。单纯重复“重试”不会触发自动迁移或上传。Emby可见性确认只使用精确输出路径，不依赖过期的原下载标题过滤。
