## 0. 执行摘要与评审意见（对初版重构计划的分析）

本设计方案基于对现有系统源码（31 个导航视图、40 余个业务组件、插件系统、`MASTER.md` 设计体系规范）及 Claude 编写的《管理端 UI 重构计划（U 阶段）》（`docs/plans/20261020-ui-redesign-plan.md`）全面深入审查后形成。

### 0.1 对 Claude 初版重构计划的肯定
1. **13 个主页面的精简收敛方向正确**：将原本过于零散的 31 个导航项归纳为“资源获取、媒体与文件、系统与运维”三大主干工作流，极大降低了管理员的认知切换成本。
2. **安全契约保留坚守原则**：计划严格遵循“预览→核对→执行→核验”四步语义、操作幂等与 202 异步排队机制、保留 302 严格直链不伪装中转或 HLS，符合本项目底层架构设计核心。
3. **技术栈与依赖零新增**：严格限定于 Vue 3 + Element Plus 2.14 + Pinia 原生实现，不引入额外重量级图表库、字体或外部 CDN，确保容器内镜像精简与构建稳定性。

### 0.2 对初版计划的 4 点改进意见与深化建议
1. **关于首页（/dashboard）信息密度与行动力的改进（采纳并深化）**：
   - *初版计划局限*：初版计划将总览放在页首，偏重展示静态指标（内存、磁盘、负载）与简单列表。
   - *改进方案*：首页必须转型为**“操作型总览工作台（Actionable Workbench）”**。将服务链路的 `readiness`（115、CD2、STRM、Emby）置于最上方，并引入**“待处理事项收件箱（Actionable Inbox）”**（聚合失败任务、待确认入库、系统告警、待确认插件等），让管理员一眼获知“今日需要我做什么”，点击即可直接直达处理面板。
2. **关于“入库整理”与“文件管理”边界的清晰化（关键修正）**：
   - *初版计划局限*：在 `/organize`（入库整理）与 `/files`（文件管理）中，STRM 相关功能分散在文件浏览、STRM 目录与 STRM 工具三个地方，导致用户在处理媒体刮削入库后仍需跳转到文件页查找 STRM。
   - *改进方案*：明确职责分工——
     - `/organize` 专注于**“媒体生命周期”**：扫描识别、待确认候选、已入库资产、归档回收与整理对账。
     - `/files` 专注于**“物理与逻辑文件层”**：云盘/本地文件浏览器、STRM 目录与生成、STRM 批量修复工具（将原 `StrmToolsView` 与 `StrmView` 合并为 `/files` 内的标签页）。
3. **关于异步结果与幂等重试的界面呈现（深化安全契约）**：
   - *初版计划局限*：初版文案强调“不把 operationKey 甩给用户”，但未给出如何呈现“未知状态”、“排队中”和“重复提交防护”的具体交互模式。
   - *改进方案*：设计通用的 `AsyncResultBanner` 与 `StateView` 规范：界面显示“任务已进入执行队列，编号 #xxxx，正在后台同步”，并保留防重提交遮罩。若发生网络抖动返回未决状态，展示黄色警告“上一操作结果正在向服务端核对中，已为您锁定表单避免重复提交”，彻底消除用户的“多击焦虑”，且不暴露底层 Go 内部变量名。
4. **关于首次使用配置向导（Wizard）的实现方式（落地细化）**：
   - *改进方案*：向导不采用侵入式全屏模态框，而是作为首页工作台的**“引导进度卡（Checklist Card）”**，根据 `/readiness` 接口动态推导完成度（4 步：① 接入 115 授权与 CD2 挂载 → ② 配置 Emby 播放网关 → ③ 添加首个 PT 站点与模板 → ④ 设置目录分类规则）。未配置时置顶展示；全部完成后提供“收起”并常驻在系统设置中支持随时回看。

## B. 首页（总览工作台）深度设计

### B.1 页面定位与数据来源契约
首页不再只是被动的只读指标监视器，而是全站的**“操作中枢与行动收件箱”**。它的目标是：让管理员在打开系统 3 秒内获知：
1. **服务通不通**：115 授权、CD2 挂载、STRM 生成与 Emby 播放是否处于健康态（`/api/v1/readiness`）。
2. **今天有什么需要我介入**：失败任务、待确认识别候选、未处理告警、待确认权限的插件实例（聚合请求）。

### B.3 “待处理”收件箱（Actionable Inbox）设计
收件箱由前端组合并发请求聚合而成（`Promise.allSettled`），任一子请求失败不阻塞其余项呈现：
1. **失败任务（Failed Jobs）**：来自 `GET /api/v1/jobs/browse?state=failed&pageSize=5`。当条数 > 0 时呈红色危险徽标，展示错误概要，点击按钮携带 `jobId` 直达 `/ops?tab=jobs&q=...`。
2. **待确认识别（Pending Candidates）**：来自 `GET /api/v1/library/candidates?pageSize=5` 中 `cloudState === 'needs_confirmation'`。条数 > 0 时呈橙色提醒，点击直达 `/organize?tab=candidates` 批量确认工作台。
3. **未确认告警（Active Alerts）**：来自 `GET /api/v1/ops` 中 `alerts` 数组中 `state === 'active'` 且未 `acknowledged_at` 的项。支持一键调起 `/api/v1/ops/alerts/{code}/ack` 静音或跳转 `/ops?tab=alerts`。
4. **待审核插件（Plugin Reviews）**：来自 `GET /api/v1/plugins` 中 `state === 'needs_action'` 或 `desiredState === 'disabled'`（升级扩权后停用）。点击调起权限确认弹窗或直达 `/plugins`。
5. **宁静就绪态（All Clean）**：当所有待办为 0 时，收件箱折叠为绿色轻量条目：`✔ 当前所有后台任务与媒体链路运行平稳，无待处理异常`。

### B.4 链路状态卡片（Readiness Indicators）交互状态机
基于 `GET /api/v1/readiness` 契约，每个卡片根据返回的 `state`、`nextAction`、`reason` 动态展现不同的状态徽标与引导主操作：

| 链路组件 (`components[key]`) | state 状态 | 页面展现徽标 | 呈现文案 (reason 解析) | 主操作按钮 (nextAction 映射) |
|---|---|---|---|---|
| **open115** | `ready` | 🟢 正常 | 115 官方 API 鉴权有效，配额信息已同步 | [查看配额] → `/connections?tab=storage` |
|  | `authorization_required` | 🔴 需授权 | 尚未绑定 115 账号或凭据已过期 | [去扫码授权] → 弹出 115 扫码弹窗 |
|  | `disabled` | 🟡 未启用 | 授权凭据存在但已被管理员停用 | [启用服务] → `/connections?tab=storage` |
|  | `check_failed` | 🔴 异常 | 最近一次连接探测失败 | [查看原因] → `/connections?tab=storage` |
| **clouddrive2** | `ready` | 🟢 正常 | 本地挂载目录可读写，云盘结构对账正常 | [浏览文件] → `/files?tab=browser` |

## C. 13 个主页面布局草图（文字与 ASCII 线框）

每个主页面的设计严格遵循 `MASTER.md` 的工作台范式：
- **统一顶部**：页面标题 + 一句话说明 + 唯一突出主操作（Primary Action）+ 次要辅助操作（Secondary Actions）。
- **同步标签页**：基于 URL Query（如 `?tab=...`）的选项卡，切换不丢状态、刷新可恢复。
- **状态感知（StateView）**：清晰区分 加载中（Skeleton/Loading）、空数据（Empty）、操作失败（Error）、权限限制（Unauthorized）与能力不支持（Unsupported）。
- **统一列表区与详情抽屉（DetailDrawer）**：表头简洁利落，危险操作二次确认，复杂 JSON/底层信息收纳于折叠区。

## D. 关键流程的步骤化交互规范

为了保证操作逻辑清晰、新手用户简单易上手、资深管理员不误操作，系统定义了 **8 大核心业务闭环流程**，所有多步操作严格遵循“步骤化、可视化、强反馈”的设计原则。

### D.1 首次使用向导（4 步闭环）
当系统 `/api/v1/readiness` 指示核心链路尚未就绪，或管理员首次初始化登录后，首页顶层展示**“新手就绪引导卡（Onboarding Card）”**，引导用户按顺序完成核心 4 步：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 🚀 欢迎使用 Media Tool · 完成以下 4 步配置即可开启自动影视闭环                         │
│ [ ① 连接云盘与挂载 (就绪) ] ── [ ② 关联 Emby (待配置) ] ── [ ③ 添加站点 (待配置) ] ── [ ④ 设定分类 (待配置) ] │
└────────────────────────────────────────────────────────────────────────────────────────┘
```
1. **第 1 步：连接云盘与挂载（115 + CloudDrive2）**：
   - 交互：点击“去授权”，弹窗展示 115 官方 App 扫码登录组件。扫码完成后，自动带出当前账号昵称、VIP 有效期与剩余存储配额。接着引导确认 CloudDrive2 的挂载路径（如 `/Volumes/CloudDrive`）。
   - 结果核验：调用 `/api/v1/integrations/{id}/test` 确保读写正常，打上第一步完成对勾。
2. **第 2 步：关联 Emby 播放服务**：
   - 交互：填写 Emby 服务内网地址与 API Key。系统提供“连通性测试”按钮。
   - 结果核验：测试通过后确认网关端口（默认 8091）与直链播放模式（严格 302 原画直链）。
3. **第 3 步：添加首个 PT 站点**：
   - 交互：从内置站点模板库中勾选目标站点（如 HDSky / OurBits），填入个人 Cookie / Passkey 凭据。
   - 结果核验：保存后触发一次轻量连通探测，同步用户魔力值与分享率。
4. **第 4 步：设定目录分类规则**：
   - 交互：提供默认推荐分类模板（“电影”、“国产剧”、“欧美剧”、“日本动画”），用户确认云盘对应存储路径。
   - 结果核验：保存规则。此时引导卡显示“全部配置完成！”，自动折叠为完成徽章，首页转入日常监控态。

### D.4 扫描识别入库（对账、候选确认、改名与归档）
媒体整理入库是本系统的核心流程，采用“机器智能预判 + 人工兜底核对”的可靠模式：
1. **触发扫描**：在 `/organize?tab=candidates` 点击“立即扫描”，选择待整理的云盘下载根目录，后台启动增量扫描 Worker。
2. **候选识别分析**：系统通过文件名提取引擎与 TMDB API 进行模糊推断。
   - **高置信度（Confidence > 95%）**：自动规划规范化路径（如 `/电影/肖申克的救赎 (1994)/肖申克的救赎 (1994) - 2160p.mkv`），生成建议。
   - **低置信度或多重歧义**：标记为 `needs_confirmation`，进入待确认工作台。
3. **批量与手动确认**：
   - 管理员在表格中勾选多个条目，点击“批量确认入库”。
   - 若遇到识别错误条目，点击“手动修正”，弹窗搜索正确的 TMDB 条目，选定对应季数与集数。
4. **生成入库工单与执行**：
   - 系统生成变更执行计划，移动/重命名云盘文件。
   - 同步在本地生成对应的 `.strm` 文件与元数据 `.nfo` 文件。
   - 旧版本或已被替代的文件安全移动至 `.media-tool-retired` 归档目录，防范直接误删。

---

### D.5 文件批量操作（预览 → 审批 → 执行 → 核对）
涉及多个文件的重命名、移动或清理，严格执行 `PreviewApprove` 流程：
1. **步骤 1：生成预览（Preview）**：
   - 用户选择待处理文件与规则后，调用 `/api/v1/files/batches/preview`。
   - 界面渲染前后对比清单（Diff Table）：原路径 vs 目标新路径、是否有重名覆盖冲突。
2. **步骤 2：核对与审批（Approve）**：
   - 若存在重名冲突或路径越界，系统显示黄色阻断警告，必须人工消除冲突项。
   - 点击“确认批准”，生成带有有效期（如 10 分钟）的批次任务票据。
3. **步骤 3：后端受控执行（Execute）**：
   - 提交执行，页面进入进度条状态，调用 `/api/v1/files/batches/{id}/approve`。
4. **步骤 4：结果核验（Reconcile）**：
   - 执行完毕后，界面不立即宣称“全部成功”，而是重新读取目录实际状态进行对账核验，汇报真实完成数目。

---

### D.6 STRM 批量修复与播放链路诊断
1. **链路诊断（302 诊断）**：
   - 用户输入文件路径，系统请求后端 `/api/v1/strm/preview` 模拟一次真实的 302 换链流程。
   - 界面展示诊断卡片：
     - ① 文件在 115 真实存在且未被删除。
     - ② 当前播放器 User-Agent 是否在白名单中。
     - ③ 是否能成功换取 115 官方临时 CDN 直链及其有效期（如 `2026-10-20 22:30`）。
     - ④ 明确标注：“本播放服务严格采用 302 直链，不经过本服务器中转流量”。
2. **批量修复（Batch Repair）**：
   - 当域名变更、解析端口调整或凭据轮换时，在 `/files?tab=tools` 选择修复范围。
   - 系统首先计算受影响的 STRM 文件数，展示影响摘要；确认后分批重写 STRM 内的固定 URL，确保现有 Emby 播放不中断。

### D.7 系统备份与维护审批流程
为保障生产数据库安全，系统维护操作遵循严格的“审批与命令生成”原则：
1. **自动备份**：系统每日按 Cron 定时打出 PostgreSQL 数据库全量快照与配置打包，支持手动触发与“固定锁定（Pin）”防自动清理。
2. **灾难恢复审批工单**：
   - 当需要从某一备份点恢复系统时，管理员在界面点击“申请恢复”。
   - 系统展示待恢复备份的创建时间、大小与版本号，并生成一个随机会话确认短语（如 `RESTORE-20261020-CONFIRM`）。
   - 管理员在输入框手工输入该短语，点击“审批工单”。
   - **安全围栏**：浏览器界面**不直接在前端点击执行全库覆写**，而是生成一条专属的受控宿主执行命令（带有效截止时间与一次性签名），由运维人员在服务器控制台安全执行，杜绝误触灾难。

### E.3 五大核心组件契约规范

#### 1. PageHeader 页面标头
- **属性**：`title: string`, `kicker?: string` (面包屑分类), `description?: string` (面向用户的通俗说明)。

- **属性**：`state: 'loading' | 'empty' | 'error' | 'unauthorized' | 'unsupported'`, `title?: string`, `description?: string`, `retryAction?: () => void`。

- **属性**：`title: string`, `dangerLevel: 'warning' | 'critical'`, `impactScope: string` (将影响的资源清单/范围), `confirmKeyword?: string` (高危操作要求输入确认短语)。

#### 4. DetailDrawer 详情抽屉
- **属性**：`title: string`, `visible: boolean`, `technicalData?: Record<string, any>`。
- **行为**：列表行查看详情时右侧滑出（宽度 560px~720px）。上方展示对用户有意义的结构化信息（标题、时间、状态、处理建议）；下方提供名为**“技术细节与原始记录”**的折叠面板（`el-collapse`），默认收起，展开后方以只读代码块展示原生 JSON、哈希与底层 ID。

#### 5. DataTable 数据表格封装
- **特性**：内置容器区域滚动（杜绝页面级横向撑破溢出）、表头浅灰色背景置顶吸顶、空数据居中提示、分页条自动靠右对齐。
